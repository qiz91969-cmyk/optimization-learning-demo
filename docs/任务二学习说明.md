# 从临时交接材料读懂任务二Demo

## 先抓住区别

旧Demo主要回答“模型读题后能否调用求解器”。新Demo首先回答“已有资料如何按照不同学习目标，变成输入清楚、目标清楚、能检查和复用的训练模板”。

把它比作准备练习册：临时档案是一份带题目、知识卡和参考证据的备课资料；任务二决定每道练习给学生看什么、让学生交什么、如何判卷。Qwen是试做练习的学生，不负责创造参考答案；Harness是发题、收卷、查格式、调用工具和记录反馈的程序。参考答案不能因为放在同一档案里就全部发给学生。

本轮不训练权重。试做模板能发现接口和样本组织问题，但不能证明微调效果。

## 建议阅读顺序

1. 先打开 `outputs/task2_v11/任务二进度总览.html`，看工程检查、模型成绩和覆盖缺口三者的区别。`outputs/task2_demo`保留v1.0首轮，不混算两版成绩。
2. 看 `data/inputs/assignment.json`：公开题干是什么，哪些条件是教程改写，实体次序是什么。
3. 看 `data/problems/assignment.json` 与 `data/references/answers.json`：结构化问题和独立参考分开保存。
4. 看 `configs/task2/mappings.json` 和 `templates.json`：来源如何映射、四个视图各给模型什么。
5. 看 `outputs/task2_v11/instances.json` 中同一案例的四个视图，随后看 `results.json` 对应的真实回答。
6. 最后读 `task2/runtime.py` 的 `check_online`、`run_view`、`grade`，理解哪些错误能反馈、哪些只能离线评分。

## 第一步：用公开案例临时代替上游交接

`task2/core.py:archive`读取题干、已整理的问题和参考资料。它不是自动解析任务一的代码，只是一个临时适配器。正式交接到位后，应替换来源适配和字段映射，不必重写全部模板。

`map_fields`根据配置逐项取值：`source`是原材料位置；`target`是统一字段；`type`规定类型；`unit`说明单位位置；`required`决定缺失时是否停止；`conversion`记录转换。本轮只实现identity，即忠实复制，不偷偷换算数字。

统一档案保留 `process` 映射记录和数值哈希。场景只写公开民用教学，时间紧迫度为空；未知信息不为了“看起来完整”而补造。`human_review=pending`表示尚无人确认全部语义，不因自动测试通过改成已人工验收。

## 第二步：同一资料形成三类模板

| 视图 | 模型能看见 | 模型应交付 | 检查方式 |
|---|---|---|---|
| 问题理解 | 题干、明示补充、实体次序、空Schema | 结构化问题及缺失信息 | 接口检查；随后离线对齐参考问题 |
| 方法选择 | 已核验问题、场景、求解要求、候选方法卡 | 方法编号、条件编号、简短适用依据 | 方法适用规则、允许集合；开放解释待复核 |
| 工具使用·调用 | 问题、已选方法、版本化接口 | 工具名和arguments，或待补字段 | 白名单、类型、维度、次序、参数语义；再真实执行 |
| 工具使用·返回 | 问题、实际返回、状态定义 | 方案数值、目标值、状态和后续处理 | 与实际返回对应；可行性和目标重算 |

例如工人分配：题干规定5名工人、4项任务，每人至多一项、每项恰好一人。理解视图让模型整理成本矩阵；方法视图可以选专用线性指派，也可以选MILP；调用视图要求模型亲自填写名称与参数；返回视图只能解释已发生的求解结果。

这四步可分别考试。独立方法/调用/返回视图使用已核验输入，不必等待理解视图成功。报告据此不能说“模型从头到尾跑通”；只有额外的assignment串联能检验这个说法。

## 第三步：方法知识与Context Skill是什么

`configs/task2/methods.json`是版本化知识表：方法编号、算法骨架、适用条件、初始化、核心操作、停止条件、输出和工具版本。

`context(method_id, problem_type, method_version, tool_version)`是本轮的最小Context Skill：查表返回方法说明和接口，没有向量数据库，也不检索当前题的答案或参考调用。版本不匹配就停止，不自动猜一个近似版本。它是受控信息读取功能，不是另一个大模型。

工人分配允许 `assignment_jv` 与 `highs_milp`；另外三题按明示整数建模采用MILP。v1.1先按问题结构筛选候选卡，所以这三题只剩一个候选，不能据此宣称验证了多算法选择能力；工人分配也不能把非首选的合法方法一概判错。

v1.0曾把完整Schema直接给Qwen，发现它会误抄Schema里的数值范围。v1.1统一改为“空结构＋字段规则”，程序端仍使用完整Schema校验。这属于开发调整，不是模型在同一次运行中收到反馈后修复成功。

## 第四步：Harness具体检查什么

`run_view`保存每轮消息与原始文本，只允许去掉包住整个JSON的单层代码框。格式、接口和由可见输入验证的错误可以反馈，最多首轮加2次修正；不从解释文字里搜一段答案，也不改模型数字。

`check_online`不读取隐藏目标或参考最优值。方法选择根据模型已经能看到的候选卡检查；调用参数与输入问题核对；返回解释与已给出的实际返回核对。因此后两者的反馈不是泄漏未知答案。

`grade`在有界在线过程结束后才评分。理解视图与参考模型比对；调用结果代入独立参考约束重算。隐藏评分失败不继续喂给模型“你应当得到265”之类的信息。方法/返回的开放解释只能标待人工复核，不把有一段文字等同于文字正确。

当前理解检查只支持有限的模型等价：约束重排、正比例缩放、界与约束的有限转换。它不是通用数学证明器；单位标签匹配也不表示所有量纲换算均已验证。

## 第五步：实际求解与状态

`task2/tools.py`只运行注册实现，不执行生成代码。MILP由SciPy/HiGHS求解；专用指派由SciPy修改的Jonker–Volgenant实现。工具在独立子进程运行，设置求解器时限及外部时限。

- `optimal`：已得到并证明最优，可以报告目标值与方案。
- `infeasible`：已证明约束无法同时满足，不得随意删除约束。广告题最低费用395250已超过预算250000。
- `limit_reached`：达到内部限制；可能有已验证可行方案，但未证明最优，也可能没有方案。
- `solver_timeout`：外层进程超时，不能当无解。
- `unbounded`：目标无界，需要检查模型界限。
- `solver_error`：工具异常，不能当作有效数学结论。

独立返回视图在 `prepare` 中调用真实求解器，来源标记为 `verified_handoff_fixture_not_model_call`。串联返回视图只使用该次模型调用得到的结果；前一步失败，后一步不执行，不拿准备阶段的结果顶替。

## 第六步：导出和使用边界

`exports/instruction.jsonl`给出“指令—输入—目标”，`messages.jsonl`把同样内容转成system/user/assistant消息。自动回读检查字段、数值和角色；目标只进入导出示例的assistant答案，不进入在线测试请求。

方法选择有多个可接受方法，示例只展示其中一个，评分仍按允许集合判断。真实训练前还需人工复核来源、字段对应、适用解释、调用与结果，再决定目标表达和数据划分。这批开发题不可兼作未见测试集。

## 怎么运行、怎么看证据

完整命令见README。`instantiate`准备材料并真实求解；`validate`检查模板工程；`run`进行Qwen试做；`report`仅从保存的结果生成两种报告。复跑要用新输出目录，避免覆盖失败记录。

`results.json`中：`first_correct/final_correct`是首轮/最终规则核验；`feedback_repaired`表示同一次运行修正后通过；`attempts[].messages`是实际请求；`raw_text`是原始回答；`solver_result`是实际工具返回；`evaluation`是离线评分。没有 `solver_result` 表示该视图不需要工具或工具未执行，要结合form判断。

公开资料说明见“四份材料与任务二要求对照”。正式项目的8类场景、5类问题与3类骨架仍是缺口，本轮两个教学骨架和两种问题接口不能替代正式分类。
