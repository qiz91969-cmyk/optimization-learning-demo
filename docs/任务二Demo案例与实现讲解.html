本文替代进度总览作为第一阅读入口。先看题目，再看题目如何进入三类训练模板，最后看代码和真实效果。所有成绩对应 outputs/task2_v11/results.json；伪代码用于解释实际实现，不是新增功能或新的运行结果。

一、先看这四道题

四个案例不是四种正式项目问题类别。它们包含生产资源分配、工人与任务分配、预算约束三种教学情境，在当前接口中归为线性问题和指派问题两类。选择它们是为了用小问题检查任务二的模板机制，而不是证明已经覆盖正式项目全部场景。

1. 打印机生产：共享设备怎样分配

一家工厂生产彩色打印机和黑白打印机。两条生产线每天分别最多生产20台、30台；两条线还共用一台安装设备，因此每天总产量不能超过35台。彩色每台利润200，黑白每台利润70。问题是：每天分别生产多少台，总利润最高？

来源：NL4Opt 2022，记录编号 1884763091，固定版本原始数据。本地题干：data/inputs/printers.json。

本Demo保留英文题干，补充中文说明、实体名称和“产量为非负整数”的明示约定。整数要求是本Demo的建模解释，不冒充NL4Opt原始整数标注。实际给Qwen的是英文题干。

用x表示彩色台数，y表示黑白台数：最大化 200x + 70y，满足 x≤20、y≤30、x+y≤35、x,y≥0，并按Demo约定取整数。独立参考结果为彩色20台、黑白15台，利润5050。这个结果供核验，不放进问题理解或调用构造提示中。

这道题的用处：检查目标系数200/70与产能20/30是否混淆，单项上限和共享约束是否同时保留；也是本轮真实工具调用成功的案例。

2. 面包房生产：两种产品怎样共享工时

一家面包房做面包和饼干。每年搅拌机、烤箱各最多使用3000小时。每个面包占用搅拌机1小时、烤箱3小时；每批饼干分别占用0.5小时、1小时。利润分别为5和3。问题是：怎样安排产量，使年利润最大？

来源：NL4Opt 2022，记录编号 1771352861，与上题同一固定版本数据文件。本地题干：data/inputs/bakery.json。面包个数、饼干批次取非负整数也是本Demo明示补充。

用x表示面包个数、y表示饼干批次：最大化 5x+3y，满足 x+0.5y≤3000、3x+y≤3000。参考结果为0个面包、3000批饼干，利润9000。原题没有要求必须生产面包，所以0不是漏掉产品，也不能私自添加最低产量。

这道题的用处：检查模型是否能把两台设备分别写成两条约束、维持系数顺序，并验证打印机所用的线性模板能否跨案例复用。

3. 广告投放：要求本身是否矛盾

公司预算250000。广播广告每次费用5000，预计触达60500人；社交广告每次费用9150，预计触达50000人。广播至少15次、至多40次，社交广告至少35次。问题是：预算内怎样安排投放，使触达人数最多？

来源：NL4Opt 2022，记录编号 -725478241，同一固定版本数据文件。本地题干：data/inputs/advertising.json。广告次数取整数为明示补充。

这道题实际上无解：仅满足最低次数就需要 15×5000+35×9150=395250，已经超过预算250000。这里的矛盾不是代码故障，也不能通过删除最低次数来“修复”。

这道题的用处：检查模板是否允许无解结果，模型能否如实解释工具状态，而不是强行编造方案。本轮它的独立返回解读通过了规则核验。

4. 工人与任务分配：谁负责哪项工作

有5名工人W0至W4、4项任务T0至T3。每项任务必须且只能交给一名工人，每名工人最多做一项，允许一名工人闲置。成本如下，要求总成本最低。

工人 T0 T1 T2 T3
W0 90 80 75 70
W1 35 85 55 65
W2 125 95 90 95
W3 45 110 95 115
W4 50 100 90 100

来源：OR-Tools官方分配示例。本地题干 data/inputs/assignment.json 是依据教程整理的英文描述，保留成本表，不冒充NL4Opt样本。代码没有复制OR-Tools实现，实际求解使用SciPy。

一种最优分配为T0给W3、T1给W2、T2给W1、T3给W0，总成本265。独立枚举5名工人承接4项不同任务的120种分配，可核对这个最优值。

这道题的用处：同一问题既可用专用线性指派方法，也可转成MILP，适合演示“多个方法都合法”；同时检查矩阵行列顺序以及5名工人不等于5项任务。

二、这些问题交给任务二的究竟是什么

1. 先准备一份临时交接档案，不让Qwen凭空创造参考资料

每道题在进入模板前，已经整理了题干、结构化问题、方法资料、接口说明和核验参考。它们是本Demo代替任务一交接的临时材料，不是实际运行了任务一，也不是任务一已经交付了全部求解结果。

材料 当前从哪里来 在任务二中的用途
题干、来源、补充约定 data/inputs中的公开材料整理 形成题目；标明哪里有人工补充
problem_json data/problems中的已整理数学表达 方法选择和调用构造的已知条件；理解模板的隐藏参考
问题类别、可用骨架和方法卡 已整理问题＋configs/task2/methods.json规则 准备候选方法、适用条件和接口上下文
参考目标值及证明 data/references/answers.json 在线过程结束后的独立评分，不用于反馈提示
返回解读所需的实际结果 prepare调用真实求解器产生 单独测试返回解读；明确标记为已核验输入求解，不冒充模型调用

“整个档案里有答案”与“给模型的输入里有答案”是两回事。任务二的重要工作就是针对学习目标，决定哪些字段能给模型看、哪些必须隐藏。

2. 四道题都分别用于三类模板，不是一道题只属于一种模板

模板/子形式 打印机题具体收到什么 其余案例怎样替换
问题理解 原始英文题干、整数和单位说明、实体顺序、空字段约定；不提供已填写问题或5050 换成面包房、广告或工人分配的题干与补充
方法选择 已整理的利润、产能与约束；求解要求；适用候选方法卡；不提供标准所选方法 工人分配有专用指派与MILP两个候选，另外两道线性题与打印机一样只有MILP候选
工具使用：调用构造 已整理问题、已选MILP、solve_linear接口说明；不提供参考调用或解 分配默认演示solve_assignment_jv；面包房、广告用solve_linear
工具使用：返回解读 已整理问题、真实工具返回optimal/5050/[20,15]、状态说明 面包房返回9000/[0,3000]；广告返回infeasible/null；分配返回265及分配向量

因此是 4道题×4种视图＝16次独立模板测试。调用构造与返回解读同属“工具使用”，不是第四类模板。

返回解读本来就是让模型读懂“已收到的工具结果”，因此把5050提供给这个模板不是泄漏；把它提前给问题理解或调用构造才有问题。

三、我们怎样写代码，让这些模板符合要求

以下按实际执行顺序讲。伪代码中的中文函数是解释性名称；每节标出真实代码位置，便于对照。

1. 统一训练要素：先把交接材料整理成同一种结构

真实实现：task2/core.py中的 archive、map_fields；配置在 configs/task2/mappings.json。

每条映射注明来源路径、目标字段、类型、单位、是否必需和转换方式。例如，把 public.description_en 写入 task_text；把 problem.parameters 写入统一的参数字段。本轮只做identity复制，不偷偷补数字或换算单位。

# 伪代码：此处是任务二适配交接资料，不是让模型重新完成任务一
材料 = 读取(公开题干, 已整理问题, 方法知识, 工具契约, 参考资料)
统一档案 = {}
for 映射 in 字段映射配置:
    值 = 按来源路径读取(材料, 映射.source)
    检查必需字段与类型(值, 映射)
    统一档案[映射.target] = 忠实复制(值)
    记录来源路径_单位_版本_转换方式(映射)
# 未知场景属性保留为空；不猜测时间紧迫度

对应要求：基于算法元模型的训练要素提取与统一表达。当前使用教学方法卡代替正式元模型；只能说接口整理机制已经实现，不能说正式元模型集成已完成。

2. 信息分层：同一档案不能整包发给模型

真实实现：instantiate、messages，位于 task2/core.py；角色和输入白名单在 templates.json。

四个区分别是 input（题目）、process（字段映射等可核对记录）、target（参考目标）、evidence（来源和核验证据）。这里的过程不是要求模型生成冗长思维链。

# 伪代码：从同一份档案中，按当前学习目标挑选可见字段
视图 = 按模板实例化(统一档案, 模板配置)
视图.roles = {"input": 输入, "process": 映射记录,
              "target": 参考目标, "evidence": 来源与核验资料}
消息 = [系统指令, 按白名单导出(视图.roles["input"])]
# 不把整个视图序列化给模型；target和evidence不能混进题目

验证方法：把隐藏目标和证据换成测试标记，检查模型消息是否完全不变；往input塞未允许字段，程序应拒绝。对应“输入信息、过程信息与目标输出的分层组织”。

3. 问题理解模板：让模型把题意整理成约定字段

真实实现：templates.json的understanding配置；check_online和 grade 位于 task2/runtime.py；结构检查复用 demo/validation.py。

以打印机为例，要求输出 problem_type、objective、entities、units、parameters、missing_information。parameters包含利润系数、各项上限、共享约束、变量类型。模型应自己从可见题干填出这些内容。

# 伪代码：先检查能否作为结构化问题读取，再检查有没有理解正确
回答 = Qwen(题干 + 明示补充 + 空字段约定)
问题 = 严格解析JSON(回答)        # 最多去掉包住整个JSON的一层代码框
检查字段类型_维度_实体次序(问题)
# 只有在线尝试结束后，才进入隐藏参考评分
对齐结果 = 与参考问题核对(问题)  # 目标、参数、约束、单位标签等
保存原文与检查结果()

不能只看能否解析成JSON。比如把“最大利润”写成“最小产能”，即使JSON合法也不对。本轮4题都未通过此视图，说明当前模型和模板组合没有稳定完成这一学习目标。

4. 方法选择模板：从候选知识中选适用方法

真实实现：applicable、context 位于 task2/core.py；规则在 methods.json；方法和条件编号由 check_online检查。

工人分配的两种合法方法是 assignment_jv（SciPy专用线性指派，修改的Jonker–Volgenant实现）和 highs_milp（HiGHS整数线性优化）。这里不能因为参考示例选了前者，就把后者判错。

# 伪代码：输入已整理问题，不等待问题理解视图先成功
候选卡 = 按问题结构筛选(方法知识库)
回答 = Qwen(已整理问题 + 求解要求 + 候选卡)
检查(回答.method_id属于适用方法集合)
检查(回答.condition_ids与所选方法卡一致)
把自由文字explanation标为待人工复核

本轮4题的方法及条件编号均通过，但三个线性题筛选后只有一个候选，难度很低。4题通过不能解释成模型已掌握复杂算法选择，更不证明其自然语言理由全部正确。 例如面包房回答自行展开了HiGHS名称，现有自动检查并没有验证这段解释，仍需要人审。

5. 工具使用：第一步是构造真正能执行的调用

真实实现：context提供版本化工具说明，check_online检查调用，task2/tools.py执行求解。这里的Context Skill就是按方法与工具版本查说明包，不是另一个模型，也没有检索当前题的参考解。

# 伪代码：模型必须自己输出调用；程序不能拿参考调用替换它
工具说明 = context(已选方法, 问题类别, 方法版本, 工具版本)
调用 = Qwen(已整理问题 + 已选方法 + 工具说明)
if 已知条件缺失:
    检查模型是否返回待补字段，停止执行
else:
    检查工具名是否注册()
    检查arguments字段_维度_实体顺序_参数是否忠于输入()
    实际返回 = 在独立进程执行注册工具(调用)
    # 不执行模型生成的Python；外层有超时限制
    将实际方案代入独立参考约束，重新计算目标值

打印机的成功调用包含 objective=maximize、实体顺序 [color_printers, black_white_printers]、利润 [200,70]、上限 [20,30]、共享约束 [1,1]≤35 和整数类型。Qwen生成这些参数后，solve_linear实际得到 [20,15]、5050，通过独立核验。

这是独立调用视图成功：其输入已经给了正确结构化问题。它不代表打印机的自然语言理解视图也成功。

6. 工具使用：第二步是如实解释实际返回

真实实现：result模板、interpretation和 check_online。要求输出状态、目标值、方案向量、是否已证最优、后续动作和简短解释。

# 伪代码：独立测试的结果来自真实求解；串联测试只用该次真实调用结果
回答 = Qwen(问题 + 实际返回 + 状态定义)
检查(回答中的状态、方案、目标值与实际返回一致)
检查(只有optimal才能写“已证明最优”)
检查(无解时不能虚构方案，超时不能被写成无解)
如果有方案: 重新计算约束与目标
检查后续动作是否符合接口枚举，解释文字另行人工复核

广告题通过：返回 infeasible，目标值与方案均为null，不声称已证明最优，后续动作为 review_constraints。这表示提示用户检查原始要求，不意味着程序获准修改约束。

7. 反馈、复用和导出：如何证明模板不是一次性的

真实实现：run_view最多首轮加2次修正；workflow.py组织16个视图和工人分配串联；export_views、check_exports负责两种JSONL的导出和回读。

# 伪代码：可见输入能判断的接口错误可以反馈，隐藏参考不能反馈
for 次数 in range(3):
    原始回答 = Qwen(当前消息)
    if 格式与在线规则通过(原始回答):
        保存结果并结束在线尝试()
        break
    追加具体接口错误()          # 不提示隐藏的参考最优值
在线结束后再做独立参考评分()

# 同一配置换四份案例，或同一案例换不同学习目标
for 案例 in 四道题:
    for 视图 in [问题理解, 方法选择, 调用构造, 返回解读]:
        实例化并检查(案例, 视图)
导出指令输入目标JSONL()
导出角色消息JSONL()
回读检查字段_数值_角色是否一致()

这对应“面向不同学习目标的模板配置”和“模板复用、扩展与实例化验证”。124项自动化测试包含旧Demo回归和新测试，不是124个真实模型题。生成的JSONL仍标人工复核pending，不能直接宣称为已验收训练集。

四、效果怎样：不能只读红绿标签

下表为v1.1独立视图的完整规则核验。6个通过均是首轮通过，没有同次反馈修复成功。开放解释仍待人审。

案例 问题理解 方法选择 调用构造 返回解读
打印机 未通过 通过（单候选） 通过，真实求解5050 未通过
面包房 未通过 通过（单候选） 未通过，未执行 未通过
广告 未通过 通过（单候选） 未通过，未执行 通过，正确保留无解
工人分配 未通过 通过（两种合法候选） 未通过，未执行 未通过

额外的工人分配串联在问题理解阶段停止，方法、调用与返回解读未串联执行。独立测试使用各自已核验输入，所以不能把表格横向拼成一次真实成功链路。

1. 问题理解的失败，确实不只是格式问题

  • 工人分配首轮识别出任务编号和大部分矩阵，但漏掉W4对应行，entities和单位留空；反馈后又漏掉missing_information。
  • 打印机把利润最大化写成最小化，并混用产能20/30与利润系数，问题类别也写成assignment。这已经改变了原题。
  • 面包房除漏字段外，还把约束写成不符合约定的文本数组，单位含义不对。
  • 广告题把问题类别、目标结构、预算约束和部分数值关系写错。

判断：当前0.5B模型在多字段联合提取、角色区分和指令遵循上表现不足。但提示也同时包含多类问题规则，字段层级较深；没有受控对照，不能把全部原因仅归于模型规模。

2. 三个调用未通过，失败程度不同

工人分配与广告的首轮，主要数值和调用内容与给定输入相符，但最外层JSON少一个闭合括号，解析失败，求解器没有执行。反馈后模型没有补完整调用，反而生成 interface、expected_delimiter 等报错说明字段。

面包房首轮不只是缺括号：还漏了变量界和变量类型，错误加入missing_information。即使补括号，也不能认定调用正确。

这三次首轮生成都记录 finished_with_eos=true，分别约172、147、146个输出token，低于1400上限，生成约4秒。现有证据不支持“输出长度用尽导致截断”，不能只调大长度解决。 缺闭合括号更符合模型自行结束但没完成结构的现象。

这里的Harness拦截本身是正确的，但只写“未通过”掩盖了分配、广告离有效调用很近这一事实。本次额外做了只读诊断：仅在内存中为这两个首轮回答各追加一个闭合括号，随后均通过既有接口和参数一致性检查。诊断没有执行求解、没有改动原记录，也不把它们改判为模型成功；它只帮助定位格式故障。

3. 三个返回解读，首轮主要错在自定义动作名

工人分配、打印机、面包房的首轮都正确保留了工具的optimal状态、方案和目标值，并写明已证最优。但它们把next_action写成 optimize，而本接口要求 report_solution，所以完整接口核验未通过。

收到反馈后，三个回答均出现退化：把optimal改成unbounded，部分还清空方案。因此不能说这三题首轮都没读懂求解结果；首轮主要是动作枚举不合规，后续才出现状态解读错误。 首轮开放解释的充分性仍需另审。

这也暴露当前设计可以改进：next_action是我们自定义的接口字段；若项目并不要求模型规划后续动作，可以由程序按状态确定，或者作为独立子项评分，不必用一个动作词掩盖核心返回字段已正确。不过这属于新模板版本，不能悄悄改标准重算旧成绩。

4. 当前检查与反馈也有局限

结构检查分层执行、反馈长度受限，可能只报告先遇到的几处错误；没有报出其他问题，不代表其他字段正确。整段重写的反馈策略会让模型改坏已经正确的内容。以后可以试“明确错误路径＋只改该处并保留其他字段”，但需要新一轮验证，本文不声称已经实现。

方法选择的“通过”只覆盖方法和条件编号，不能证明解释文段每句话正确。报告以后应继续区分接口合规、核心语义、调用执行、独立结果以及开放文字复核，不能只给一个笼统通过率。

五、是否需要调用API，换更大的模型

判断：值得做一个小规模对照，但还不能断言必须换模型

目标如果是尽快展示任务二模板闭环，使用能力更强的指令模型做对照是合理的；继续仅靠0.5B模型反复调整同几道题，不容易分清到底是模板问题还是模型能力问题。但API只是调用途径，参数规模也不是充分保证，不能预先承诺一定跑通。

这里有三个不同问题，要用不同办法处理：

已观察的问题 优先考虑的办法 更大模型能否保证解决
JSON少括号、漏必需字段、枚举不合规 结构化输出/受约束解码，或改善格式提示 可能减少，不能靠“更大”保证
目标、约束、实体对应理解错误 更强模型对照＋检查题意与模板清晰度 值得实测，格式约束不能保证题意正确
反馈后把正确字段改错 更明确的局部纠错反馈＋模型对照 需要分别验证反馈设计和模型能力

一些推理API支持依据JSON Schema生成结构化输出；具体模型、服务商和Schema支持范围需要逐项确认。可参考Hugging Face结构化输出文档。这类功能约束输出格式，不等于证明成本、约束或状态语义正确；本地也可采用支持约束解码的推理实现，不是云端专属能力。当前本地worker没有这项机制。

推荐实验：先分开比较模型和输出机制

  1. 保留本轮16个视图作为基线，旧成绩不改。
  2. 用一个候选API模型，先按尽量一致的题目、输入白名单、模板和重试规则跑相同视图，记录模型版本、耗时、token和费用。解码参数不能完全一致时明确记下差异。
  3. 如果接口支持，再单列“开启结构化输出”的运行。这样才能区分是模型更会理解，还是接口保证了格式，不把两种变化混成一种提升。
  4. 两组都继续用同一套本地求解器与独立参考核验。报告分别给出JSON合规、核心字段、完整接口、求解和人工复核状态。
  5. 三类独立视图达到可展示水平后，再跑串联。发现失败时保留原始记录，不自动增加重试或换参考答案。

当前这4题都是公开开发题，可作为经你确认的API对照输入；不发送合同、想定、私有方案或凭证。开始前需要你决定服务商/模型、预算上限及数据使用限制，密钥通过本地环境变量配置，不粘贴进报告或Git。本次只作判断和方案说明，没有新增付费调用、换模型或重跑成绩。
