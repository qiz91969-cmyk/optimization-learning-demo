# 任务二训练模板：案例、输入、处理流程与模型对比

## 一、任务边界与基本结构

任务二处理的核心问题是：已有任务资料怎样整理成结构统一、输入与答案分开、能复用且能检查的训练模板。

本Demo暂时以公开案例整理的资料代替任务一交接，包括原始题干、已整理的问题、方法知识与工具说明。它没有实现任务一的自动解析系统，也没有进行模型微调。参考结果和核验证据是Demo另外准备的材料，不能据此认为任务一已经完成了求解。

```text
【公开题干、已整理问题、方法与工具资料】
                     ↓
【临时交接档案：统一字段，记录来源】
                     ↓
【任务二：按学习目标配置输入与参考目标】
          ┌──────────┼──────────┐
          ↓          ↓          ↓
    【问题理解】 【方法选择】 【工具使用】
                             ┌────┴────┐
                             ↓         ↓
                         【构造调用】【解读返回】
          └──────────┬──────────┘
                     ↓
【模型试做 → 在线检查 → 必要时调用工具】
                     ↓
【独立参考核验 → 保存记录 → 导出模板示例】
```

“模板”规定模型看到什么、应当输出什么、根据什么检查；“Harness”是执行这些规定的程序，负责组织消息、检查、反馈、调用工具与保存过程。模型负责生成回答，求解器负责计算。二者都不能代替独立核验。

本轮包含4道题，每题形成问题理解、方法选择、调用构造、返回解读4种视图，共16个独立测试。**调用构造与返回解读同属工具使用，因此仍是三类训练模板。** 同一道题用于不同学习目标，不是四道题分别归入四种模板。

## 二、案例描述、来源与用途

### 2.1 打印机生产与共享产能

一家工厂生产彩色打印机和黑白打印机。彩色生产线每天最多生产20台，黑白生产线每天最多生产30台。两条生产线共用一台安装设备，因此总产量每天最多35台。彩色每台利润200，黑白每台利润70。要求确定两种打印机的日产量，使利润最大。

来源为NL4Opt 2022，记录编号 `1884763091`：原始数据固定版本。Demo保留英文题干，增加中文说明、实体名称和“产量取非负整数”的明确约定。整数要求属于Demo补充，不能称为NL4Opt原始整数标注。模型实际读取英文描述。

如果x是彩色台数、y是黑白台数，则目标为最大化 `200x+70y`；约束为 `x≤20`、`y≤30`、`x+y≤35`，且x、y为非负整数。独立参考结果为20台彩色、15台黑白，利润5050。

这道题用于检查：利润系数是否与产能混淆，单项产能与共享产能是否同时保留，以及模型生成的工具参数是否忠于已给定问题。

输入文件：题干与来源、已整理问题、临时交接档案。

### 2.2 面包房设备工时分配

面包房生产面包和饼干。搅拌机、烤箱每年各最多使用3000小时。每个面包分别占用搅拌机1小时、烤箱3小时，每批饼干分别占用0.5小时、1小时；利润分别为5和3。要求确定产量，使年利润最大。

来源为NL4Opt 2022，记录编号 `1771352861`：原始数据固定版本。非负整数的计数约定为Demo明确补充。

如果x是面包个数、y是饼干批次，则目标为最大化 `5x+3y`；约束为 `x+0.5y≤3000`、`3x+y≤3000`。独立参考结果为0个面包、3000批饼干，利润9000。原题没有要求必须生产面包，因此不能私自补入最低产量。

这道题用于检查：两种设备是否分别形成约束，各产品系数是否按相同顺序排列，以及打印机案例的线性模板能否复用于另一种资源分配情境。

输入文件：题干与来源、已整理问题、临时交接档案。

### 2.3 广告预算与最低投放要求

公司预算为250000。广播广告每次费用5000、预计触达60500人；社交广告每次费用9150、预计触达50000人。广播广告至少15次、至多40次，社交广告至少35次。要求在预算内使总触达人数最大。

来源为NL4Opt 2022，记录编号 `-725478241`：原始数据固定版本。广告次数取整数为Demo明确补充。

这道题的条件互相冲突：仅满足最低投放次数就需要 `15×5000+35×9150=395250`，超过预算250000。因此正确结论是无解，而不是某个投放数量。

这道题用于检查：模板是否允许无解状态，模型能否保留原始约束，是否会把无解误认为必须删除条件才能解决的程序错误。

输入文件：题干与来源、已整理问题、临时交接档案。

### 2.4 工人与任务的成本分配

5名工人W0至W4承接4项任务T0至T3。每项任务必须且只能分配给一名工人，每名工人最多承担一项，允许一名工人闲置。成本如下，要求总成本最低。

| 工人 | T0 | T1 | T2 | T3 |
|---|---:|---:|---:|---:|
| W0 | 90 | 80 | 75 | 70 |
| W1 | 35 | 85 | 55 | 65 |
| W2 | 125 | 95 | 90 | 95 |
| W3 | 45 | 110 | 95 | 115 |
| W4 | 50 | 100 | 90 | 100 |

来源为OR-Tools官方分配示例。英文题干依据教程整理，成本矩阵保持一致；它不是NL4Opt记录。Demo没有复制OR-Tools求解实现，而是使用SciPy接口。

一种最优分配为T0交给W3、T1交给W2、T2交给W1、T3交给W0，总成本265。独立枚举5名工人分配到4项任务的120种情况，可以核对该最优值。

这道题用于检查：矩阵行列对应是否正确，“每项恰好一次”与“每人至多一次”是否区分，以及同一个问题是否接受多个合法求解方法。

输入文件：题干与来源、已整理问题、临时交接档案。

这4个案例不代表4类正式项目问题。本Demo中，打印机、面包房、广告使用 `linear` 问题接口，工人分配使用 `assignment` 接口；不能据此声称已覆盖正式方案的全部场景、问题类别和算法骨架。

## 三、输入文件与模板之间的对应关系

### 3.1 模板前的资料与模型可见输入不同

| 文件类型 | 包含内容 | 是否整份发给模型 |
|---|---|---|
| 题干文件 | 英文原文、中文说明、实体顺序、补充假设和来源 | 否，只按模板选取需要的字段 |
| 已整理问题文件 | 问题类别、目标、实体、单位、参数、约束和缺失项 | 方法选择、调用构造、返回解读可以使用；问题理解不能直接看到其答案 |
| 临时交接档案 | 汇总上述资料，并关联方法知识、工具契约、参考结果和来源记录 | 否，含隐藏参考，不能整包发给模型 |
| 各模板输入文件 | 对应视图的 `roles.input`，已经去掉隐藏目标和证据 | 作为用户消息中的数据；还会搭配模板系统指令 |

下表中的交接档案和模板输入是从**14B实测保存的实例材料**中拆出的阅读副本，不是重新生成的题目。16份模板输入均与实际首轮请求的用户消息逐项核对一致。它们不包含系统指令，完整指令见模板配置，实际完整消息见14B运行记录。

### 3.2 每道题的文件对应关系

| 案例 | 模板前的原始与整理材料 | 汇总交接材料 |
|---|---|---|
| 打印机 | 题干／问题JSON | handoff.json |
| 面包房 | 题干／问题JSON | handoff.json |
| 广告预算 | 题干／问题JSON | handoff.json |
| 工人分配 | 题干／问题JSON | handoff.json |

四题共用字段映射配置、模板配置和方法知识与工具注册表。参考答案与证明仅用于相应目标准备和事后核验，不作为所有视图的可见输入。

### 3.3 每道题实际进入各模板的输入

| 案例 | 问题理解 | 方法选择 | 工具使用：调用构造 | 工具使用：返回解读 |
|---|---|---|---|---|
| 打印机 | understanding_input.json | method_input.json | call_input.json | result_input.json |
| 面包房 | understanding_input.json | method_input.json | call_input.json | result_input.json |
| 广告预算 | understanding_input.json | method_input.json | call_input.json | result_input.json |
| 工人分配 | understanding_input.json | method_input.json | call_input.json | result_input.json |

这些文件的用途各不相同：

- 问题理解输入是题干、补充、实体顺序和空字段说明，不包含已填写的目标问题。
- 方法选择输入是已整理的问题、场景、求解要求和候选卡，不提供“标准应选方法”。
- 调用构造输入是问题参数、已选方法及接口说明，让模型生成调用，不直接提供参考调用。
- 返回解读输入包含实际工具返回，因为该任务就是解释一个已经得到的结果。这不属于答案泄漏；但不能把这个返回提前给问题理解视图。

阅读副本的出处、哈希和请求一致性记录见输入副本清单。副本仅为方便查看，不替代原始数据或正式验收。

## 四、字段整理与信息分层

### 4.1 训练要素的统一表达

字段映射相当于一份转换清单：规定从哪里取值、放到哪里、数据应该是什么类型、单位在哪里说明、缺了能否继续。本轮转换方式为忠实复制，不擅自补数字、转换单位或猜测场景属性。

```text
【题干文件＋问题文件＋方法和工具资料】
                      ↓
【按映射清单读取字段】
  来源路径 → 目标字段
                      ↓
【检查必需项、类型与问题结构】
         ├─ 缺失或不合法 → 【报错，保留待处理问题】
         └─ 合法 → 【统一档案＋来源/版本/转换记录】
```

实际代码：core.py中的 `archive` 负责组织材料，`map_fields` 依据mappings.json转换；`validate_problem`检查问题结构。典型字段如下。

| 字段 | 含义 | 作用 |
|---|---|---|
| task_text | 原始英文任务描述 | 问题理解的题目依据 |
| supplement | 明示补充，例如整数约定、单位、实体名称 | 把人为约定公开，避免模型和核验采用不同假设 |
| problem_class / problem.problem_type | 当前问题类别 | 确定可用结构及方法规则 |
| problem.objective | maximize或minimize | 明确优化方向，不与目标系数混淆 |
| problem.entities | 决策对象及其顺序 | 使向量、矩阵和解能对应到对象 |
| problem.parameters | 成本或利润、约束、变量界、类型等 | 构成可执行数学问题 |
| problem.missing_information | 尚缺少的已知条件 | 避免在资料不完整时编造调用 |
| method_knowledge / algorithm_skeletons | 方法说明和适用骨架 | 为选择方法与读取工具上下文提供依据 |
| tool_contracts | 工具字段、方法版本及使用约定 | 约束调用方式，避免猜工具接口 |
| reference_result | 独立参考结果和证明 | 用于核验，不随其他字段全部发送给模型 |

目前场景只标明公开民用教学，时间紧迫度为空；正式项目场景分类和上游元模型版本尚未接入。该机制对应“基于算法元模型的训练要素提取与统一表达”，但当前验证的是临时材料适配，不是正式元模型已集成。

### 4.2 输入、过程、目标和证据分开保存

```text
【一份统一档案】
       ↓  按当前学习目标组织
┌────────────────────────────────┐
│ input     模型此刻可以看到的资料 │
│ process   字段映射、转换等记录   │
│ target    参考目标或可接受集合   │
│ evidence  来源与核验证据         │
└────────────────────────────────┘
       ↓  只从input白名单提取
【系统指令＋用户输入】 → 【大模型】

【target、evidence】 → 【在线尝试结束后的参考核验】
```

实际代码：core.py中的 `instantiate`创建分层视图，`messages`只从允许字段构造消息。过程记录是可检查的字段映射和转换，不是要求模型输出长篇内部推理。

检查办法包括：替换隐藏目标与证据后，模型消息应保持不变；往input中放入未允许字段，应被拒绝；模板版本或定义变化后，旧实例不能不加检查地混用。对应要求是“输入信息、过程信息与目标输出的分层组织”。

## 五、三类模板的处理流程

### 5.1 问题理解模板

**学习目标：**把自然语言描述整理成约定的问题字段，而不是直接猜最优值。

输入为 `task_text、supplement、entity_order、field_contract`。其中field_contract提供空结构和字段规则；结构形状由当前已整理问题类别辅助确定，因此这不是完全无辅助的通用问题识别。输出应包括类别、优化方向、实体、单位、参数及缺失项。

```text
【题干＋补充条件＋实体顺序＋空字段说明】
                         ↓
【模板拼接消息】 → 【模型填写结构化问题】
                         ↓
【在线检查：JSON、字段、类型、维度、实体顺序】
         ├─ 不通过 → 【接口错误反馈】 → 【最多再答2次】
         └─ 通过
                ↓
【离线核验：目标、参数、约束与参考问题是否对应】
                ↓
【记录结果；不把隐藏参考答案反馈给模型】
```

打印机题需要把利润写为 `[200,70]`，把共享设备写为 `[1,1]≤35`，并保留单项上限20/30及整数变量要求。面包房要保存两台设备的两条约束；广告要保留全部预算和最低次数；工人分配要保存5行4列成本矩阵。

实际代码：templates.json的understanding配置定义任务；runtime.py中的 `check_online`执行在线检查，`grade`在事后与参考问题比对；validation.py提供JSON Schema和维度检查，evaluation.py提供有限的数学表示对齐。

这种安排把“能否按结构表达”和“是否理解正确”分开。合法JSON并不证明语义正确；单位标签相同也不证明量纲转换正确。

本轮效果：0.5B为0/4通过，14B为3/4通过。14B的打印机题格式正确，但将整数变量写成continuous，独立参考核验未通过，详见末尾对比。

### 5.2 方法选择模板

**学习目标：**根据已整理的问题与候选方法知识，给出适用方法和条件依据。

输入为 `problem、scenario、requirements、candidates`；输出为 `method_id、condition_ids、explanation`。这里不再让模型先读自然语言重建问题，而是提供已核验的数学表达，单独检验方法选择模板。

```text
【已整理问题＋场景＋求解要求】
                    ↓
【规则筛选候选方法卡】
                    ↓
【模型选择方法，并给出条件编号与简短依据】
                    ↓
【检查方法是否适用、条件编号是否对应】
       ├─ 不合法 → 【反馈并有限修正】
       └─ 合法 → 【记录规则通过；解释文字待人工复核】
```

工人分配有两个合法候选：专用线性指派 `assignment_jv` 和通用MILP `highs_milp`。前者使用SciPy修改的Jonker–Volgenant实现，不笼统称作匈牙利算法；后者通过SciPy调用HiGHS。打印机、面包房和广告按Demo的整数线性表达筛选后，都只有MILP候选。

实际代码：core.py中的 `applicable`进行规则筛选；methods.json保存方法编号、骨架、适用条件、核心操作、停止条件、输出和工具版本；runtime.py检查方法和条件编号。

模板的参考目标是允许方法集合，不是只能接受一个固定名字。对于合法替代方法，不因示例选择不同而判错；但解释文段不能仅凭“非空”就认为可信。

本轮效果：两种模型均为4/4通过方法与条件编号检查。三个单候选案例难度较低，不能将这个结果解释为模型已具备复杂算法决策能力；开放依据仍需复核。

### 5.3 工具使用模板：调用构造

**学习目标：**按照已选方法的接口，把问题参数组织成可以执行的调用。

输入为 `problem、selected_method、context`。context包含方法摘要、工具名称、版本、参数字段与次序要求；它不包含当前案例的参考调用或参考最优解。输出为 `tool_name、arguments`；已知条件缺失时应输出待补字段。

```text
【问题参数＋已选方法】
             ↓
【Context Skill按方法与版本读取接口说明】
             ↓
【模型生成工具名＋arguments】
             ↓
【检查工具白名单、字段、数值、矩阵次序及版本】
       ├─ 已知条件缺失 → 【返回待补字段，不执行】
       ├─ 调用不合法   → 【反馈并有限修正】
       └─ 调用合法
                  ↓
【独立进程运行注册的SciPy工具】
                  ↓
【用独立参考约束重算方案与目标 → 保存实际返回】
```

Context Skill在本轮是一个受控查表函数，不是另一个模型，也不是复杂知识库检索系统。它按方法、问题类别和版本取工具说明；版本不匹配即拒绝，不猜接口。

以打印机为例，模型生成 `solve_linear`，arguments中保留maximize、两种实体、利润 `[200,70]`、共享约束、上下界和整数类型。通过检查后工具才真正运行，得到 `[20,15]`、5050。

实际代码：core.py的 `context`读取说明；runtime.py检查调用并将合格调用交给tools.py的 `solve`；SciPy进行真正求解，evaluation.py独立复算。程序不执行模型生成的Python，也不以参考调用顶替失败回答。

本轮效果：0.5B为1/4通过，14B为4/4通过。14B四个调用都真实执行，其中广告得到无解，这属于正确求解状态，不是工具执行失败。

### 5.4 工具使用模板：返回解读

**学习目标：**解释已经收到的工具结果，保留方案、目标值与状态，并给出符合约定的后续处理。

输入为 `problem、actual_return、status_definitions`。输出包括 `status、values、objective_value、optimality_proven、next_action、explanation`。

```text
【问题要求＋实际工具返回＋状态定义】
                         ↓
【模型输出：方案、目标值、状态、后续动作】
                         ↓
【检查是否忠于实际返回】
  数值不能改；无解不能编方案；超时不能写成无解
                         ↓
【有方案则重新计算约束与目标】
                         ↓
【规则核验结果＋待人工复核的文字解释】
```

几种状态需要分清：

| 状态 | 含义 | 不应误解为 |
|---|---|---|
| optimal | 找到方案并已证最优 | 仅仅找到一个可行方案 |
| infeasible | 已证明条件不能同时满足 | 程序报错，或允许自行删约束 |
| limit_reached | 达到内部限制；可能有可行解，但未证最优 | 必然无解或必然最优 |
| solver_timeout | 外层等待求解超时 | 数学问题无解 |
| unbounded | 目标在给定条件下无界 | 没有可行方案 |
| solver_error | 工具异常 | 有效数学结论 |

实际代码：core.py的 `STATUS_ACTIONS`定义动作映射；runtime.py检查状态、目标值、方案及后续动作；开放解释继续标记待人工复核。

本轮效果：0.5B为1/4通过，14B为4/4通过。0.5B三个有解题首轮已保留正确数值和状态，但把动作写成不允许的optimize，随后反馈导致状态退化。不能仅凭最终失败就说它首轮完全没有理解结果。

独立返回视图采用准备阶段真实求解得到的材料，并明确标记来源；它不必等待同题的调用视图成功。只有额外串联测试才要求使用前一步模型调用的实际返回。

## 六、复用、验证与代码组织

### 6.1 同一配置跨案例复用

```text
【同一套模板配置】
       ├─ 替换题目 → 【打印机／面包房／广告／工人分配】

                              ↓

                              ↓
【回读检查：字段、数值和角色是否保持一致】
```

实际代码：workflow.py组织材料准备和验证；core.py的 `export_views、check_exports`负责两种格式。读取导出示例时，assistant目标是供学习的参考答案；在线测试不能把这部分一起当输入发给模型。

本轮提供的是可追溯模板示例，不是已人工验收的训练集。进入训练前还需复核来源、补充假设、数学模型、解释文字和目标表达，再决定划分与使用方式。已用于开发的这些题不能继续被当作未见测试集。

### 6.2 独立测试与串联测试

```text
独立测试：
【各自已核验的输入】 → 【分别测试4种视图】
作用：前一个目标失败，不遮住后一个目标的表现。

串联测试：
【题干】 → 【模型整理问题】 → 【模型选择方法】
        → 【模型生成调用＋工具执行】 → 【模型解读返回】
作用：检查前一步实际产物能否供后一步使用。
任一步未通过核验 → 【记录失败；后续不执行】
```

本轮额外串联案例为工人分配。不存在用参考问题替换模型错误输出、再把整条链路算作成功的处理。

## 七、0.5B与14B的实测结果对比

### 7.1 实验条件

两组均使用v1.1模板、同一套方法规则和四道公开题。0.5B在本机由Transformers运行，14B通过SSH隧道调用服务器Ollama；本机仍负责模板、Harness、SciPy工具和独立核验。

14B实际模型为 `qwen2.5:14b`，GGUF Q4_K_M量化版本。两侧硬件、量化、推理实现、上下文默认值和请求时限不同，不能将结果差异严格归因于模型规模。此次没有为14B新增强制JSON/Schema输出机制。

16份首轮消息中12份逐字相同；4份返回解读消息仅实际基准求解耗时不同，其余内容相同。模板、映射和方法配置哈希一致。差异已保留，后续更严格的比较可使用冻结的同一份返回材料。

### 7.2 总体结果

| 指标 | 本地Qwen2.5-0.5B | 服务器Qwen2.5-14B |
|---|---:|---:|
| 独立视图数 | 16 | 16 |
| 首轮完整规则核验通过 | 6 | 15 |
| 最终完整规则核验通过 | 6 | 15 |
| 首轮在线接口检查通过 | 6 | 16 |
| 首轮原生JSON可解析 | 9 | 16 |
| 尝试总轮数 | 36 | 16 |
| 同次反馈后修复成功 | 0 | 0 |
| 调用视图真实工具执行次数 | 1 | 4 |
| 独立视图累计耗时，含重试 | 328.529秒 | 252.695秒 |
| 工人分配四步串联 | 在问题理解停止 | 四步通过 |

14B累计耗时较少，部分原因是没有进行重试；这不是纯推理速度比较。所有“通过”均指当前规则核验，解释文字仍待人工复核，不代表正式项目验收或模型总体正确率。

| 案例 | 问题理解 | 方法选择 | 调用构造 | 返回解读 |
|---|---|---|---|---|
| 打印机 | 失败 → 失败 | 通过 → 通过 | 通过 → 通过 | 失败 → 通过 |
| 面包房 | 失败 → 通过 | 通过 → 通过 | 失败 → 通过 | 失败 → 通过 |
| 广告预算 | 失败 → 通过 | 通过 → 通过 | 失败 → 通过 | 通过 → 通过 |
| 工人分配 | 失败 → 通过 | 通过 → 通过 | 失败 → 通过 | 失败 → 通过 |

按视图汇总：问题理解由0/4变为3/4；方法选择维持4/4；调用构造由1/4变为4/4；返回解读由1/4变为4/4。新增加9个通过视图，没有原本通过而后来失败的视图。

### 7.4 具体改进与剩余问题

**问题理解。** 0.5B存在实体留空、漏字段、错用目标系数和约束等问题。14B在面包房、广告和工人分配上通过了核验，但打印机仍有错误：输入明确要求非负整数，它却输出 `variable_type=continuous`。利润与约束基本正确，不代表变量类型也正确。

14B将打印机的单项上限写进constraints、upper_bounds设为null，这种表达本身允许。失败点是整数/连续类型，不是上限换了存放位置。虽然本题连续松弛也恰好得到5050，仍不能忽略输入中已声明的整数要求。

**调用构造。** 0.5B在工人分配和广告的首轮主要是少了一个闭合括号，导致调用无法执行；面包房还漏掉变量界和类型。14B四道题均生成合法调用并真正执行，独立核验得到分配265、打印机5050、面包房9000和广告无解。

**返回解读。** 0.5B的三个有解题首轮已经保留正确方案、目标值和optimal状态，但把next_action写成optimize；反馈后又误改为unbounded。14B四题均通过状态与数值核验。这说明改进包含结构遵循与状态保持，不只是求解数字发生变化。

**反馈能力。** 14B只有打印机的事后参考核验未通过；其在线结构检查已经通过，因此没有触发修正。参考答案没有作为反馈再次交给模型。本轮两组都没有真实反馈修复成功，不能声称更换14B已证明反馈机制有效。

### 7.5 串联结果与可得结论

```text
0.5B工人分配：
【问题理解未通过】 → 【方法／调用／返回未执行】

14B工人分配：
【问题理解通过】 → 【方法选择通过】
        → 【模型调用＋真实求解通过】 → 【返回解读通过】
```

14B串联中各步使用前一步的实际产物，没有用独立测试的参考输入替换失败内容。这提供了一条任务二四步连续运行的真实成功记录，但仅限于这个工人分配案例；其他题没有因此自动获得串联成功结论。

当前结果支持：模板与Harness能够接入不同模型，在这个小规模公开案例集上，14B减少了结构化输出和调用错误，并完成了一条串联。仍需处理整数约定遵循、解释文字核验和更有区分度的方法选择案例。它不证明模型微调有效，也不表示完成正式方案要求的全部覆盖。

核验依据：0.5B完整运行记录、14B完整运行记录、自动生成的比较数据、模型对比报告。本文引用已保存实测，没有重跑模型或重新修改成绩。
