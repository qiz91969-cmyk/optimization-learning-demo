# 从一道题读懂代码

建议顺序：先运行打印机JSON入口，看5050怎样得到；再运行自然语言入口，观察模型能否自己填写相同参数。最后才阅读批量报告。不要先打开一个很长的运行轨迹去猜字段。

## 一次运行里谁负责什么

模型像读题并填表的同学；模板是表头和填表规则；Harness是收表、检查、转交计算的程序；求解器按数学条件计算；独立评估器拿另一份参考题核对。参考题不是模型的提示。

这只是比喻。模型输出来自已有神经网络权重的推理，本次没有loss、梯度更新或训练。反复给它报错重新回答，也不意味着权重改变。

## 三个容易混淆的JSON

1. `data/inputs/printers.json`是公开题干档案。英文原题说明20、30、35、200、70分别是什么。中文解释给人看。
2. `data/problems/printers.json`是整理后的参考问题。运行`--entry json`时直接把它交给程序，不经过模型读题。
3. `outputs/时间/printers_nl.json`是某次真实运行档案，包含模型到底写了什么、检查的结果和工具的实际返回。它可能是错的，不是标准答案。

同一台电脑上同时存在“正确的problem文件”和“模型生成的问题”，并不表示程序把正确文件塞给了模型。隔离边界在run_demo.main：`nl`传给run_online的problem参数是None；在线运行结束才加载参考文件做评估。

## problem字段与参数

`problem_type`是固定的linear、assignment、transportation之一。linear在本Demo同时覆盖生产与广告等线性资源配置，不专指某一种生产算法。`objective`只能是maximize或minimize。

`entities`给出数组次序。打印机为[color_printers,black_white_printers]；系数[200,70]按相同次序对应。次序错了，即使数字都对，问题也可能已经变了。

`units.quantity`说明变量数量的单位；`units.objective`说明目标值单位；每条线性约束还带`unit`。程序只检查单位标签存在，并在离线阶段对比部分标签，不能自动证明小时/分钟或每年/每天没有混用。

`parameters`是模型填写、工具真正需要的数据。`missing_information`列出缺失信息；非空时停止执行，不编造缺失值。当前5道题均按完整输入整理，不是开放世界的补问系统。

|linear参数|含义|打印机例子|
|---|---|---|
|objective_coefficients|每个变量在目标里的系数|[200,70]，即200x+70y|
|constraints|共同限制的列表|共享机器限制x+y<=35|
|constraints[].name|便于阅读的标签|shared_capacity，不决定计算|
|constraints[].coefficients|本约束中每个变量的系数|[1,1]|
|constraints[].sense|<=、>=或=|<=|
|constraints[].rhs|右边的限制数字|35|
|constraints[].unit|该限制的单位标签|printers/day|
|lower_bounds|每个变量的下界|[0,0]|
|upper_bounds|每个变量的上界；null表示没有单项上界|[20,30]|
|variable_type|continuous连续或integer整数|integer，来自公开补充约定|

assignment的parameters只有tasks和cost_matrix。entities是工人，tasks是工作；每行对应一名工人、每列对应一项工作。固定接口内置“每人至多一项、每项恰好一人”，超出此约定的排班题不在支持范围内。

transportation的parameters包括destinations、supply、demand、cost_matrix、variable_type。entities是仓库；supply对应仓库，demand对应销售点，cost_matrix对应每条连接的单位运输费。固定接口内置“供应上限、需求下限”，没有默认增加虚拟仓库、短缺采购或路线规则。

## 从入口逐个函数跟读

### run_demo.main

argparse把`--entry json`等终端参数转换成Python值。Path以脚本所在目录为基准找文件。main逐题调用run_online，先保存不含评分的`*_online.json`，再调用evaluate_record得到评估版本。输出新时间目录，不覆盖以前的试验。

### prompts.template_hint和make_messages

公开英文中有warehouse选配送，有worker选分配，否则在已声明的线性练习范围内选linear。它只是透明的教学规则，不能称为通用语义理解。混合worker与warehouse会提示范围不支持。

make_messages构造四条消息：system规则、独立虚构教学题、该教学题的结构化示例、新题题干。当前v4只展示当前类别，并明确列出六个必填顶层字段。实体顺序由公开数据提供。例题不是这5道题的参考答案，新题数字必须重新提取。完整请求保存在轨迹中，可以亲自检查。之前v2使用占位词，小模型会直接照抄，因此弃用；v3只强调模仿示例，仍经常漏字段，失败记录全部保留。

### backend.LocalQwen.generate与model_worker.main

新环境中没有再装2GB的PyTorch。LocalQwen用subprocess启动旧环境Python，将消息通过stdin交给worker。worker用local_files_only=True读取本机权重，用apply_chat_template组成模型习惯的对话格式，将文本变成token编号后执行generate。

torch.inference_mode表示不计算训练梯度；eval关闭训练行为；float16减少显存占用。do_sample=False使用确定性的生成策略，但不同软件/硬件下仍不承诺逐字完全一致。最多生成1000个token，生成软限时45秒，父进程90秒硬超时。

程序得到原始文本后，通过stdout的JSON协议传回来。报错和库警告走stderr；元数据记录模型版本、库版本、生成耗时和显存峰值。不会执行模型生成的字符串，也没有调用付费API。

### validation.parse_model_output

json.loads将文本解析为字典；它不是大模型，也不知道题目含义。若文本是完整单层Markdown代码框，可去掉外框再解析，同时标记fence_removed。不会静默修改数值、不补逗号、不从大段解释里偷取一个JSON。重复键、NaN、Infinity和根节点不是对象都被拒绝。

### validate_problem与build_call

JSON Schema像一份机器可读的表格规则，检查字段是否存在、number是否真的是数字、objective是否在允许值中。后续Python代码检查数组长度、矩阵行列、ID是否重复、上下界等。

build_call把类别映射到固定工具名，将objective、entities、units、parameters放进arguments。arguments不是结果，而是函数的输入参数。这个包装过程没有重新决定哪个算法更好：模型已填写数值，程序只是按固定接口转交。

### harness.run_online

for循环最多执行3轮：首轮加2次修正。每一轮都保存原始响应。格式不对时，把具体错误和原有对话再交给模型；不是告诉它标准答案是什么。模型报告缺数据则停止，不能靠默认参考值补齐。

真实求解返回optimal、infeasible或unbounded都结束在线尝试。需要独立评估判断这是正确结论还是模型漏了约束。模型崩溃/超时不应反复占用资源，直接记录。失败达到上限就失败，不为展示好看而替换答案。

### solver.compile_model与solve_direct

求解器需要数值矩阵，不理解英文。compile_model把共享限制变成A的行，把约束右边变成上下界，把变量上下界和整数标记分别传入。

SciPy的linprog处理连续LP，milp处理整数模型。最大化会先对目标系数取负以适配最小化接口，返回结果再用原系数重算目标。assignment用0/1变量，transportation用非负运输量；矩阵展开为行优先。

solve_isolated在另一个进程运行求解器，内部10秒限时，外部20秒硬超时。超过限制时返回明确状态，不能把临时候选解标成最优解。

### evaluation.feasible_and_value与aligned

feasible_and_value将实际返回值代回另一份参考问题，逐条检查原题限制并重算目标。它不调用求解矩阵构造函数，减少同一构造错误同时污染求解与验证的风险。

aligned额外检查问题结构对齐，允许约束换序、正比例缩放以及把变量上界写成约束，但不是万能的数学等价证明器。它不检查生成文字推理的正确性，也不能取代人工源文核对。

单位标签不同、复杂等价形式或其他未识别表达可能要求人工复核。评估失败要看具体字段，不应直接断言所有失败都是数学解错误。

## 运行档案字段

|字段|该怎么看|
|---|---|
|record_type/mode|真实模型、结构化入口还是人工故障测试|
|prompt_version/public_template_hint|用了哪版提示、哪条公开规则选了模板|
|attempts[].messages/raw_text|真正发给模型的消息及模型真正返回的原文|
|raw_json_valid|原文能否直接作为JSON对象解析|
|fence_removed/normalized_json_valid|是否清理外框、清理后能否解析；不是模型自己纠错|
|schema_valid|结构与部分关系检查是否通过，不代表题意对|
|problem/tool_call|模型提取结果、程序准备调用的白名单工具及arguments|
|solver_result.status|optimal、infeasible、unbounded、超时或错误|
|solver_result.values/objective_value|变量值及目标；无解时为空|
|feedback|仅在线接口错误反馈；不是参考标准答案|
|model_metadata|Qwen版本、库版本、耗时、生成长度、显存与警告|
|online_status|环路是否执行完，与题目答对不同|
|evaluation|在线结束后的独立评分，不能反向作为重试提示|
|first_pass_verified/final_verified|首轮/最终是否通过参考核验|
|input_sha256/reference_sha256|输入和参考资料指纹，便于识别后来是否改过|

## 三段真实记录怎样读

以下均对应固定v4的 `outputs/20260919_230138_672269/`。这不是为讲解伪造的响应，打开相应JSON即可逐项对照。

### 例一：打印机JSON入口，先看清求解链路

打开 `printers_json.json`。这个入口没有模型回答，raw_text为空是正常的。run_online直接接收已整理的问题，再经validate_problem、build_call、solve_isolated、evaluate_record。

|原题事实|进入problem的位置|交给求解器的含义|
|---|---|---|
|每台彩色利润200、黑白70|objective_coefficients=[200,70]|最大化200x+70y|
|分别最多20、30台|upper_bounds=[20,30]|x<=20，y<=30|
|共享机器每天最多35台|constraints中的[1,1]、<=、35|x+y<=35|
|本演示按整台计数|variable_type=integer|x、y只能为非负整数|

工具名为solve_linear，arguments包含目标方向、实体、单位、参数。实际返回值为[20,15]和5050，随后评估器代回参考限制：20<=20、15<=30、20+15<=35，目标200×20+70×15=5050。测试还用有限枚举确认没有更好方案。

这证明题目结构化以后能正确传参、求解和检查。它没有证明模型能从英文自动得到上述条件。

### 例二：工人分配自然语言入口，模型到求解器

打开 `assignment_nl.json`。按 `attempts[0].messages`、`raw_text`、`problem`、`tool_call`、`solver_result`、`evaluation` 的顺序读。

模型看到的是英文题干、公开实体顺序和格式说明，以及另一道2人2任务的虚构例子，不会看到成本265或最优分配。真实输出提取了5个工人、4个任务、完整5×4成本表、minimize及空缺失信息列表。

build_call将problem_type=assignment映射为solve_assignment。它不是让模型再选一种算法；parameters中的成本矩阵保持模型提供的数值，程序不会用参考文件替换。

求解时生成20个0/1变量。按W0到W4的行顺序、T0到T3的列顺序展开；每列加起来=1，每行加起来<=1。真实返回可读作：

|工人|承接任务|成本|
|---|---|---:|
|W0|T3|70|
|W1|T2|55|
|W2|T1|95|
|W3|T0|45|
|W4|闲置|0|

总成本265。记录中的-0.0与0.0数值相同，不是负分配。参考核验检查原题约束、重新累加成本并与120种分配的独立枚举结果比较，最终通过。human_review仍是pending，不能将程序通过说成人工通过。

本次约11.894秒包含加载模型、生成和子进程等；solver_result内约0.0029秒只指求解阶段，不能混用这两个时间。这题首轮成功，不是反馈修复成功。

### 例三：配送自然语言失败，Harness的价值和局限

打开 `transportation_nl.json`：首轮正确提取供给[1000,4000]和需求[500,900,1800,200,700]，但parameters缺cost_matrix和variable_type。Harness给出的错误只是这两个字段必填，并未发回正确成本矩阵或8600。

第二轮模型确实补出了题干中的矩阵，却把entities改成空数组、problem_type改成接口不允许的optimization，供给和需求也不再保留。第三轮仍不合规，达到上限后停止。没有调用求解器，没有自动从参考资料填回丢失字段。

因此，Harness像检查员：它能阻止不合规表格流向计算程序，却不能保证填表的人会改好。它也不能仅靠字段齐全判断某个费用是否抄错。前者需要模型改进，后者还需要独立的题意、模型及结果核验。

面包房题还出现照搬示例上限[8,9]的情况。这表明few-shot例子虽可能帮助格式，也可能带来数值混淆。例题不是隐藏答案，但模型仍可能误用，必须保留真实输出才能发现。

## 哪些内容仍然没有完成

没有训练模型，没有自由多算法选择，没有任务一正式交接，没有真实业务部署，没有大规模数据集，也没有人工审核全部样本。5题结果是开发集观察。下一步优先复核数据和失败轨迹，而不是用更多重试次数把成功率堆高。
