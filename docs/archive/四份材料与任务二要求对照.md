# 四份材料与任务二要求对照

核对日期：2026-09-20。本文件只整理公开资料。项目内部合同与方案不复制、不提交到仓库。本轮对应任务二四项要求，但不表示完成正式项目的全部覆盖。

## 1. OptiMUS仓库

来源：https://github.com/teshnizi/OptiMUS

它是一套利用语言模型解决优化问题的研究代码：组织问题资料、建立数学表达、生成求解代码、执行，并根据错误或检查结果调整。仓库存在不同版本/分支；当前主分支与2023年论文不能视作同一个固定实现。本轮阅读README和主分支 `main.py`、`parameters.py`，不复制该系统代码，不宣称复现其成绩。主分支为可变引用，本项目未将其作为运行依赖。

借鉴位置：`task2/runtime.py`保存逐轮输入输出、把明确的接口错误反馈给模型；`task2/workflow.py`把临时资料、模板、运行和评价分开。不同于其自由生成代码的路线，本项目只允许注册工具，不执行Qwen生成的Python。模型自报置信度也不作为正确性证据。

仓库提到的NLP4LP数据在Hugging Face存在访问条件。本轮未下载、未使用，不将数据卡可见等同于已获取样本，也不把它计入案例来源。

## 2. 2023年论文

来源：https://arxiv.org/abs/2310.06116 （PDF：https://arxiv.org/pdf/2310.06116）

论文研究的是自然语言描述到优化建模与求解的自动化组织方式。可借鉴之处是分离问题描述、数值资料和输出要求，并围绕建模、执行和检查形成有限修正过程。论文与后续仓库版本的机制、数据及结果分别理解，不能用后续仓库替代论文实验依据。

借鉴位置：`configs/task2/mappings.json`定义来源与目标字段；`templates.json`定义不同学习任务的输入和输出；`task2/core.py`将同一案例形成多种视图。这里引用的是方法组织思路，不采用论文结果作为本Demo的成绩，也不复用其任意代码执行方式。

## 3. NL4Opt 2022

来源：https://nl4opt.github.io/

2022任务聚焦优化题文本的实体识别与线性规划逻辑形式生成。它不是现成的“三类工具学习模板数据集”，但题干、字段与数学表达的对应关系适合用来制作问题理解视图和检查跨案例模板复用。

本轮实际使用已有本地记录：打印机 `1884763091`、面包房 `1771352861`、广告预算 `-725478241`。原始定位：
https://github.com/nl4opt/nl4opt-competition/blob/49f1e0d66b7fdcd33305a7f281c2a7c13f5620ea/generation_data/test.jsonl

使用方式：保留公开题干和来源，复用已整理的问题记录；补充整数约定、单位和实体次序时在 `modeling_notes_en` 明示，不冒充原始标注。本地模型、方法卡、工具调用及独立证据属于本项目的教学整理，不声称全部由NL4Opt提供。原始测试划分进入本项目开发后，不能再当作未见测试集。

许可与署名：沿用仓库 `THIRD_PARTY_NOTICES.md` 中的NL4Opt MIT说明。

## 4. NL4Opt 2024

来源：https://nl4opt.github.io/neurips-2024/
配套页面：https://nl4opt.github.io/neurips-2024/starterkit/ 、https://nl4opt.github.io/neurips-2024/evaluation/

2024版本扩展到由文本建立LP/MIP模型及生成可执行建模程序，评价涉及求解结果。它和本项目“从问题资料到方法/工具使用”有参考关系，但不能简单理解为2022数据换了一种说法。

本轮采用：参考建模结果可执行、求解状态和目标值需要检查的评价思路。实际实现还检查参考问题、原始约束和变量类型，不把“目标值相同”当作所有语义均正确。

未采用：官网指向的 `https://github.com/nl4opt/nl4opt-competition-v2` 在核对时返回404，未取得的数据不计入使用量。starterkit页面的总量与LP/MIP分项数量存在不一致，本项目不引用该数量作为验收或规模依据。未来找到可访问版本后，应重新检查许可、来源和结构。

## 5. 工人分配与求解接口的补充来源

工人分配题依据OR-Tools官方教程整理，成本矩阵保持一致，题干明确标为改写，不是NL4Opt记录：
https://developers.google.com/optimization/assignment/assignment_example

专用方法采用SciPy 1.16.2的 `linear_sum_assignment`，文档称其为修改的Jonker–Volgenant算法，不笼统标成匈牙利算法。矩形矩阵允许部分工人闲置；本Demo要求每个任务均被分配，工人数少于任务数时明确无解。
https://docs.scipy.org/doc/scipy-1.16.2/reference/generated/scipy.optimize.linear_sum_assignment.html

另一合法方法为SciPy `milp` 接口调用HiGHS。两种方法适用不表示性能相同，本轮不做优劣比较。
https://docs.scipy.org/doc/scipy-1.16.2/reference/generated/scipy.optimize.milp.html

## 与任务二四项要求的对应

| 要求 | 本轮实现 | 不应夸大的结论 |
|---|---|---|
| 训练要素提取与统一表达 | 规则化映射公开题干、问题、方法资料和参考信息，保存类型、单位、版本与来源路径 | 不是任务一自动理解系统，也不是正式元模型已交接 |
| 信息分层 | 输入、过程、目标、证据分开，模型消息按白名单导出，离线参考不用于反馈 | Schema不能自动理解全部题意 |
| 模板配置 | 问题理解、方法选择、工具使用三类；工具使用含调用与返回两个子形式 | 四种视图不等于四类训练模板 |
| 复用、扩展与实例化验证 | 四题复用配置、16视图、双JSONL往返、版本和故障测试、真实模型实测 | 没有训练模型，也没有完成正式方案全部场景和问题类型 |
